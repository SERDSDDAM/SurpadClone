تمام — بخصوص “تطبيق المسّاح” (FieldApp)، هذا وضعه الحالي وما يلزم لإغلاقه 100% مع خطة تنفيذ قصيرة، وربط واضح بالمسارين Shapefile/GNSS ونموذج الفرع التنفيذي/المكتب الإشرافي.

أولاً: حالة تطبيق المسّاح الآن
- ما يعمل:
  - التقاط نقاط GNSS وإرسالها بنجاح (POST/GET) بعد توحيد الاستجابة.
  - عرض النقاط والرسوم الأساسية على الخريطة، مع محاكاة RTK ودقة محسوبة.
  - إدارة جلسة مسح (زمن الجلسة، حالة الاتصال، مؤشرات GNSS).
  - تكامل مع سير العمل: يرفَع بياناته على طلب محدد (SR-…)، ثم يكمل الفرع الاعتماد.
- ما تبقى (سهل الإغلاق خلال 5–7 أيام):
  - ربط GNSS حقيقي عبر Bluetooth/NMEA (إلى جانب المحاكاة).
  - وضع أوفلاين كامل: IndexedDB + Queue + مزامنة تلقائية عند الاتصال.
  - أدوات هندسية عملية (Snap/Modify) للخطوط والمضلعات.
  - بوابة QC قبل “إكمال المسح” (عتبات دقة/إغلاق مضلع/عدد نقاط).
  - تصدير/استيراد GeoJSON/CSV داخل الجلسة.
  - زر تصعيد ميداني سريع لوسم “street_issue” عند الحاجة (يرسل Flag ويحوّل الفرع للمكتب).

ثانياً: ربط التطبيق بالآلية المزدوجة (Shapefile/GNSS)
- إسقاط سابق (Shapefile):
  - التطبيق اختياري هنا. الرفع يتم من الويب (Desktop) غالباً.
  - إن رغب الفريق الميداني: إتاحة “رفع Shapefile من الجهاز” عبر واجهة بسيطة (ZIP) مع QC.
- إسقاط جديد (GNSS):
  - التطبيق هو المسار الإلزامي: تجميع نقاط/خطوط/مضلعات → QC مسبق → إكمال المسح → يعتمد الفرع → PDF.

ثالثاً: عقود الـ API النهائية لتطبيق المسّاح
- نقاط:
  - POST /api/survey-requests/:id/points
    body: { pointNumber, latitude, longitude, elevation?, accuracy?, featureCode?, notes? }
    response: { success:true, point:{…} }
  - GET /api/survey-requests/:id/points
    response: { success:true, data:[{…}], count }
- ميزات (خط/مضلع):
  - POST /api/survey-requests/:id/features
    body: { featureType:'line'|'polygon', pointIds:[…], featureCode?, notes? }
    response: { success:true, data:{…} }
- إنهاء المسح:
  - POST /api/survey-requests/:id/complete → { success:true, request:{ status:'survey_completed', … } }
- تصعيد ميداني (زر داخل التطبيق):
  - POST /api/survey/requests/:id/escalate { escalationReason:'street_status', notes }

ملاحظة: في الواجهة احرص على جلب المصفوفة دوماً هكذا:
const arr = Array.isArray(resp) ? resp : (resp?.data ?? []);

رابعاً: بوابة QC قبل الإرسال (Gate)
- دقة GNSS:
  - fixType ∈ {RTK_FIXED, RTK_FLOAT, 3D}، والافتراضي المقبول لإغلاق المسح: RTK_FIXED أو RTK_FLOAT.
  - HDOP ≤ 1.5 (مسموح حتى 2.0 مع تنبيه).
- إغلاق هندسي:
  - polygon: ≥ 3 نقاط، ST_IsClosed=true، ∆الإغلاق ≤ 20 سم/محيط القطعة ≤ 0.3%.
- كفاية العينة:
  - نقطة لكل ركن + نقاط كافية لأضلاع طويلة (≥ 2 نقاط لكل ضلع > 50م).
- التحقق المكاني:
  - PnP داخل حدود المخطط/الحي/القطاع، إن لم يكن: تنبيه + خيار تصعيد.

خامساً: أوفلاين ومزامنة
- IndexedDB: جداول pointsQueue, featuresQueue, sessions.
- عند offline:
  - enqueue لكل POST، status=‘pending’.
- عند online:
  - background sync، retries مع backoff، وإزالة من الطابور عند success.
- مؤشرات UI: “دون إنترنت”، “عنصر/عناصر معلّقة”، زر “مزامنة الآن”.

سادساً: ربط الجهاز GNSS (حقيقي)
- دعم Bluetooth SPP / BLE مع قراءة NMEA (GGA/RMC/GST) أو Socket (TCP/IP) إن توفر.
- محوّل NMEA → {lat,lng,alt,hdop,vdop,fixType,satellites}.
- شاشة “الأجهزة المتصلة”:
  - GNSS: متصل/غير متصل، قوة الإشارة، fixType، عدد الأقمار، RTK age (إن متاح).
  - إعادة محاولة تلقائية عند فقد الاتصال.

سابعاً: مهام Sprint لإغلاق 100% (5–7 أيام)
- اليوم 1:
  - QC Gate في التطبيق: تحقق العتبات قبل POST /complete.
  - توحيد responses + معالجة كل الحالات في FieldApp.
- اليوم 2:
  - Offline Queue (IndexedDB + UI Indicators).
  - تصحيح أي اختلافات schema/response.
- اليوم 3:
  - Snap & Modify للخط/المضلع + إظهار أطوال/مساحات فورية.
- اليوم 4:
  - GNSS حقيقي: طبقة adapter لنصوص NMEA (واجهة اختيار الجهاز، بدء/إيقاف).
- اليوم 5:
  - تصعيد ميداني (زر سريع) + تعليق تلقائي للطلب pending_office_review.
- اليوم 6–7:
  - Export/Import (GeoJSON/CSV)، تقارير جلسة (avg HDOP, pointsCount)، تحسينات UI، اختبارات E2E.

ثامناً: خطة UAT لتطبيق المسّاح (مكثفة يوم واحد)
- سيناريوهات:
  1) التقاط نقاط RTK ثابت + إكمال المسح → اعتماد فرع → PDF.
  2) HDOP مرتفع (ترفض الإكمال مع توجيه).
  3) مضلع غير مغلق (يمنع الإكمال).
  4) Snap/Modify يعمل والتحديثات تُحفظ.
  5) أوفلاين: التقاط نقاط + مزامنة ناجحة عند الاتصال.
  6) تصعيد “street_issue” من الميدان → يظهر بالمكتب.
- معايير نجاح:
  - 0 أعطال UI/JS.
  - كل POSTات المعلّقة تُرفع بعد الاتصال.
  - زمن عرض/تفاعل ≤ 200ms متوسط، رسم سلس.
  - دقة الحفظ = الدخل (لا تبديل lon/lat، لا تقليم أرقام غير مقصود).

تاسعاً: الحوكمة والأمان
- توثيق الدخول: JWT قصير العمر + refresh.
- ربط الجهاز (اختياري): deviceBinding لتقليل إساءة الاستخدام.
- تشفير محلي للـ IndexedDB (على الأقل تشفير الحقول الحساسة).
- RBAC: surveyor فقط يضيف/يعدّل نقاط، supervisor يعتمد وغلق الطلب.

عاشراً: تدريب المسّاحين (جلسة 2–3 ساعات)
- ساعة نظرية: السياسة، العتبات، متى التصعيد.
- ساعة عملية: GNSS/أوفلاين/مزامنة/Snap/إكمال المسح.
- 30 دقيقة: أسئلة/أخطاء شائعة (swap lat/lng، إغلاق مضلع، فقد اتصال GNSS).

ملحق – أمثلة رسائل واضحة داخل التطبيق
- “لا يمكن إكمال المسح: HDOP أعلى من الحد المسموح (1.5). يرجى تحسين الاستقبال أو التصعيد للمكتب.”
- “لا يمكن إغلاق المضلع: الفارق الهندسي أكبر من 0.3%. أضف نقاطاً إضافية للأضلاع الطويلة.”
- “تم تسجيل 3 نقاط في وضع دون إنترنت. سيتم المزامنة تلقائياً عند الاتصال.”

باختصار
- تطبيق المسّاح جاهز وظيفياً؛ وما تبقى هو إغلاق أوفلاين/GNSS الحقيقي/QC gate وبعض الأدوات الهندسية. بخطة 5–7 أيام نصل 100%.
- أقترح البدء غداً بتنفيذ Sprint أعلاه مع UAT ميداني ليوم واحد؛ وبعده Go/No-Go للطرح على فرع نموذجي.

إذا رغبت، أبدأ الآن بتمكين Offline Queue وQC Gate في FieldApp وربط زر “تصعيد ميداني”، أو أجهّز لك حزمة APK (PWA + Android) للتوزيع التجريبي الداخلي.
